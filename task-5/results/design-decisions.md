# Task 5. Зафиксированные архитектурные решения

## Принятые решения

| Область | Решение | Обоснование |
|---|---|---|
| **Метрики** | Prometheus + Micrometer | Стандарт для Java/Spring; метрики Spring Batch, JVM, HTTP, БД — из коробки через Micrometer |
| **Дашборды** | Grafana | Стандарт для визуализации Prometheus; единый интерфейс для метрик и логов (Loki) |
| **Логирование** | Grafana Loki + Promtail | Лёгкий стек, интегрирован с Grafana; достаточен для 400k строк/сутки; не нужны мощности Elasticsearch |
| **Оповещения** | Prometheus Alertmanager | Стандарт для self-managed Prometheus; маршрутизация, дедупликация, группировка алертов |
| **Каналы оповещений** | Slack + Email | Основной канал для команды — Slack; email — для формальных уведомлений и эскалаций |
| **Сбор метрик с VM** | Node Exporter | Стандартный экспортер для CPU/RAM/disk/network; интегрируется с Prometheus |
| **Сбор метрик с JVM** | Micrometer + Spring Boot Actuator | Встроено в Spring Boot; не требует агентов |
| **Сбор логов с контейнеров** | Promtail (sidecar или DaemonSet) | Читает stdout контейнеров и пушит в Loki |

## Почему не ELK

- Loki легче в эксплуатации: один бинарник + объектное хранилище.
- Elasticsearch требует больше ресурсов (JVM + heap + диски).
- Для 400 000 строк/сутки и небольшой команды ELK — избыточен.
- Loki интегрируется с Grafana, где уже будут дашборды метрик.
