# Task 2. Сравнение технологических решений

## Сравнительная таблица

| Критерий | Spring Batch | Apache Airflow | K8s CronJob | Spark |
|---|---|---|---|---|
| **Наличие конфигурации CRON-расписания** | 🟡 Нет встроенного планировщика. Требуется `@Scheduled` (без HA), Quartz или внешний K8s CronJob как обёртка | 🟢 Нативный CRON в `schedule`. Полноценный планировщик с историей, backfill, timezone | 🟢 Нативный `CronJob` в K8s. Часть стандартного API. Ничего ставить не нужно | 🔴 Планировщика нет. Нужен внешний оркестратор (Airflow, CronJob, Oozie) |
| **Сложность реализации логики обработки** | 🟡 Java-код: `ItemReader` + `ItemProcessor` + `ItemWriter`. Готовые JDBC-ридер и FlatFile-райтер. Но требуется писать и собирать приложение | 🟡 Python DAG. Логика через операторы. Для тривиального ETL — просто. Но нужны DAG-и, конфиги, метабаза | 🟢 Можно на любом языке. Тривиальный ETL на Python: `psycopg2` + `csv` + `boto3`. ~100 строк кода | 🔴 DataFrame API, драйвер, executor’ы, настройка ресурсов. Оверкилл для 10k строк |
| **Ресурсоёмкость решения** | 🟡 JVM-приложение. Если в режиме сервиса — постоянно ест память. Если в CronJob — ресурсы только во время запуска | 🔴 Webserver + scheduler + metadata DB + workers работают **постоянно**, даже когда DAG не выполняется | 🟢 Под запускается раз в сутки на 10–30 секунд. В простое — ноль потребления | 🔴 Драйвер + N executor’ов. Кластер Spark держит ресурсы, даже если данных мало |
| **Масштабируемость под нагрузкой и сложность реализации** | 🟡 Партиционирование задач (partitioning). Работает, но сложно настраивается. Параллелизм через `TaskExecutor` | 🟡 Горизонтальное масштабирование через Celery/K8s executor. Мощно, но настройка сложная | 🟢 Параллельные Job-ы: `parallelism`, `completions`, `Indexed Job`. Всё декларативно в манифесте | 🟢 Лучшая масштабируемость в таблице. Но под 10k строк это не имеет значения |
| **Сложность развёртывания в облаке и интеграции с микросервисами** | 🟡 Java-приложение → Docker-образ → K8s. Нативно, если микросервисы на Java. Иначе — новый язык в стеке | 🔴 Ещё один стек. Managed (MWAA, Cloud Composer) дорого, self-managed — сложно. Метабаза, RBAC, секреты | 🟢 Родная среда K8s. Ничего нового: манифест, ConfigMap с SQL, Secret с креды, ServiceAccount | 🔴 Spark Operator, драйверы, executor’ы, специфичные для Spark CRD. Существенная инфраструктура |
| **Удобство интеграции с логированием и мониторингом** | 🟡 Micrometer + Prometheus. Работает, но нужно настраивать в приложении. Логи в stdout — нативно | 🟢 Prometheus exporter из коробки. Логи в stdout. Grafana-дашборды публичные. Очень удобно | 🟢 Родной K8s-стек. Логи → Loki/ELK, метрики → Prometheus, всё уже настроено для других сервисов | 🟡 Spark UI + event logs. Специфичная модель, требует отдельного мониторинга |

### Вывод

Для данной задачи оптимален **K8s CronJob с тривиальным ETL-контейнером на Python**, читающим из PostgreSQL, формирующим CSV на каждого B2B-клиента и складывающим результат в S3. Решение нативно для существующей инфраструктуры, минимально по ресурсам, легко развёртывается, интегрируется со штатным мониторингом и имеет понятный путь масштабирования.
