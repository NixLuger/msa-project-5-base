# Task 2. Верхнеуровневый план имплементации

## Обзор

Решение — **K8s CronJob**, который каждое утро в 06:00 формирует кастомные
CSV-прайс-листы для B2B-клиентов из PostgreSQL и складывает их в S3.

План разбит на 7 этапов: от подготовки инфраструктуры до эксплуатации.
Каждый этап самодостаточен и заканчивается проверяемым результатом.

## Ключевые архитектурные решения

- **Один последовательный поток** — цикл по клиентам внутри одного запуска.
  Проще в разработке и отладке; пути масштабирования заложены на будущее.
- **Идемпотентность** — повторный запуск за ту же дату перезаписывает файлы,
  а не дублирует их.
- **Изоляция ошибок по клиентам** — падение на одном клиенте не валит
  весь процесс, но фиксируется в итоговом статусе.
- **Push-модель метрик** — короткоживущий под не даёт собрать метрики pull-ом,
  поэтому используется Pushgateway.
- **Внешние секреты** — доступы к БД и S3 не хранятся в манифестах
  и не коммитятся в Git.

## Этапы

### Этап 1. Подготовка инфраструктуры

Что нужно сделать перед разработкой:

- Создать S3-бакет для прайс-листов и настроить политику жизненного цикла.
- Завести сервисные учётки: read-only пользователь в PostgreSQL,
  сервисный аккаунт в S3.
- Подготовить K8s namespace и ServiceAccount с минимальными правами.
- Настроить хранение секретов (Sealed Secrets / External Secrets Operator).

**Результат:** инфраструктура готова, доступы выданы, секреты не в Git.

### Этап 2. Разработка ETL-приложения

Логика приложения:

1. Подключиться к PostgreSQL и получить список активных клиентов.
2. Для каждого клиента выполнить JOIN по 4 таблицам и сформировать CSV.
3. Загрузить файл в S3 с ключом, включающим дату запуска.
4. Собрать метрики и отправить их в Pushgateway.
5. Завершиться с кодом 0 (успех) или 1 (ошибки).

Отдельно прорабатывается:

- Обработка ошибок: падение на клиенте не валит весь Job, но влияет
  на итоговый exit code.
- Логирование в структурированном виде (JSON) для сбора Loki/ELK.
- Покрытие юнит- и интеграционными тестами, включая тест на идемпотентность.

**Результат:** рабочее приложение, протестированное локально.

### Этап 3. Контейнеризация

- Собрать минимальный Docker-образ (multi-stage build, non-root user).
- Прогнать сканер уязвимостей.
- Запушить образ в registry.
- Проверить работу контейнера с dev-БД и dev-S3.

**Результат:** воспроизводимый образ в registry.

### Этап 4. K8s-манифесты и деплой

- Описать CronJob: расписание, политика конкурентности, лимиты ресурсов,
  retry-политика, таймауты.
- Описать ConfigMap (SQL-запросы) и Secret (доступы).
- Использовать Kustomize для различий между dev / stage / prod.
- При наличии GitOps (ArgoCD/Flux) — завести синхронизацию из Git.

**Результат:** манифесты в Git, деплой воспроизводим в любую среду.

### Этап 5. Мониторинг и логирование

- Убедиться, что логи пода попадают в общий стек (Loki/ELK).
- Настроить отправку метрик через Pushgateway в Prometheus.
- Создать дашборд в Grafana: статус последнего запуска, длительность,
  количество файлов, ошибки по клиентам.
- Настроить алерты: падение Job, отсутствие успешного запуска за сутки,
  превышение времени выполнения, ошибки по клиентам.

**Результат:** решение наблюдаемо теми же инструментами, что и остальные
микросервисы магазина.

### Этап 6. Тестирование

- **Локально:** полный цикл с Postgres и MinIO в Docker.
- **Dev:** ручной запуск CronJob, проверка S3, метрик, логов.
- **Stage:** прогон на реалистичных данных, проверка алертов,
  имитация сбоев БД и S3.
- **Приёмка:** согласование формата CSV с бизнесом, проверка интеграции
  с B2B Portal.

**Результат:** решение проверено в условиях, приближенных к prod.

### Этап 7. Деплой в production и эксплуатация

- Раскатать CronJob в prod, дождаться первого запуска по расписанию.
- Первые дни — пристальный мониторинг алертов и дашбордов.
- Написать runbook для дежурного: что делать, если Job не отработал.
- Зафиксировать пути масштабирования: переход на `Indexed Job`
  при росте числа клиентов или времени выполнения.

**Результат:** стабильно работающее решение, готовое к эксплуатации.

## Риски

| Риск | Митигация |
|---|---|
| Недоступность БД или S3 | Retry на уровне Job, алерты |
| Рост числа клиентов | Изоляция ошибок, план на `Indexed Job` |
| Утечка секретов | External Secrets, минимальные права, ротация |
| Дублирование файлов | Идемпотентность по дате |
| Слишком долгий запуск | Таймауты, метрика длительности, алерт |

## Критерии готовности

- CronJob работает в production по расписанию.
- CSV генерируются на всех активных клиентов, B2B Portal их читает.
- Логи, метрики и алерты подключены к общему стеку.
- Runbook написан, решение передано в эксплуатацию.

## Оценка трудозатрат

Порядок величины: **1.5–2 недели** на одного разработчика
при наличии готовой инфраструктуры и процессов CI/CD.
