| Элемент | Описание |
|---|---|
| **Контекст** | Маркетинговый отдел формирует отчёты, объединяя данные из разнородных источников: CSV-файлы со статусами доставок, PostgreSQL с заказами, платежами и расширенными данными пользователей, Kafka с цепочкой событий по модификации заказов. Пайплайн должен гибко конфигурироваться, поддерживать ветвление, условные переходы, event-триггеры, интеграцию с BigQuery, Redshift, Kafka и Spark, а также иметь встроенный мониторинг, оповещения, retry и email-уведомления. Ожидаемый объём — около 1 млн записей за запуск. |
| **Причина** | Задача сформулирована как оркестрация пайплайнов, а не как реализация batch-логики внутри одного приложения. Нужны UI, история запусков, декларативные retry, ветвления и готовые коннекторы к внешним системам. Spring Batch — это processing-фреймворк для JVM: он умеет читать/обрабатывать/писать чанками, но не даёт из коробки планировщик, UI, event-триггеры и богатый набор провайдеров. Закрывать эти требования через Spring Batch пришлось бы сборкой из Spring Cloud Data Flow, Micrometer, JavaMailSender и клиентских библиотек — это дороже и медленнее. |
| **Принято** | Использовать **Apache Airflow** как оркестратор пакетной обработки. Пайплайны описываются как DAG. Ветвление — через `BranchPythonOperator` и `ShortCircuitOperator`, event-триггеры — через datasets и сенсоры, retry и email-уведомления — декларативно на уровне задач. Интеграции с BigQuery, Redshift, Kafka и Spark — через официальные provider-пакеты. Тяжёлая обработка 1 млн записей выносится в Spark/SQL/BigQuery, Airflow управляет их запуском. Локально разворачивается через официальный `docker-compose`, в облаке — через MWAA, Cloud Composer, Astronomer или Kubernetes. |
| **Отклонено** | **Spring Batch** как основное решение. Причины: нет встроенного UI, планировщика и event-триггеров; интеграции с BigQuery, Redshift, Kafka и Spark собираются вручную из разных библиотек; мониторинг и оповещения требуют отдельного стека (Micrometer + Prometheus + Grafana + JavaMailSender); локальный POC менее нагляден для сдачи Task1; выше порог входа и объём кода для демонстрации тех же возможностей. |
| **Цель** | Единая точка оркестрации пайплайнов с наглядным UI и историей запусков, декларативными retry, ветвлением, email-уведомлениями и event-триггерами. Быстрый локальный POC и очевидный перенос в облако. Готовые модули под BigQuery, Redshift, Kafka и Spark, ускоряющие разработку. Возможность масштабировать обработку за счёт внешних вычислителей без переписывания оркестрации. |
| **Компромиссы** | Airflow сам не обрабатывает данные — он оркестрирует, поэтому тяжёлую логику нужно выносить в Spark/SQL/BigQuery, что добавляет отдельные компоненты. Python как язык DAG может быть неудобен, если команда стандартизирована на Java/Spring. Локальный `docker-compose` требует ресурсов (Postgres, scheduler, webserver, workers). В облаке managed-варианты (MWAA, Cloud Composer) стоят дороже self-managed. Принимаем осознанно: выигрыш в скорости разработки, наблюдаемости и готовых интеграциях перекрывает эти издержки. |


# Task1 — POC пакетной обработки на Apache Airflow

## Что здесь

Локально развёрнутый Apache Airflow + PostgreSQL + MailHog.
Один DAG `etl_pipeline`, который:

1. Читает заказы из PostgreSQL.
2. Читает статусы доставок из CSV (файловая система).
3. Анализирует данные и считает долю заказов без доставки.
4. Ветвится: `alert_path` (проблема) или `ok_path` (всё хорошо).
5. В `alert_path` включена retry-политика (3 попытки, интервал 10 сек).
6. При успехе и неуспехе DAG отправляет email через MailHog.

## Как запустить

```bash
docker compose build
docker compose up -d
docker compose ps
```

З.Ы. использовать docker-compose-v2


## Сценарии для демонстрации

Все три сценария прогнаны локально, скриншоты лежат в `screenshots/`.

### Сценарий A — ветка `alert_path` с retry

**Настройки:** по умолчанию (`threshold = 0.1`, `alert_fail_always = false`).

**Что происходит:**

1. `analyze` считает `missing_ratio = 0.25` (20 заказов, 15 доставлено).
2. `branch_by_threshold` выбирает ветку `alert_path`, `ok_path` → `skipped`.
3. `alert_path` падает на попытках 1 и 2 (симуляция нестабильного API),
   на попытке 3 завершается успешно.
4. DAG завершается успешно, `on_success_callback` шлёт письмо SUCCESS.

**Что показывает сценарий:**
- ветвление пайплайна по условию;
- retry-политика (видно Attempt 1/2/3 в логах);
- XCom с метриками;
- email-уведомление об успехе.

**Скриншоты:** `screenshots/step_1_alert_branch/`

- список DAG-ов с активным `etl_pipeline`;
- Graph View с ветвлением;
- `alert_path` в статусе `up_for_retry` (жёлтый);
- финальное состояние — `alert_path` зелёный, `ok_path` розовый (`skipped`);
- логи `alert_path` с Attempt 1/2/3;
- XCom задачи `analyze` с метриками;
- письмо SUCCESS в MailHog.

### Сценарий B — ветка `ok_path`

**Настройки:** Variable `missing_ratio_threshold = 0.5`.

**Что происходит:**

1. `analyze` считает `missing_ratio = 0.25`.
2. `branch_by_threshold` видит `0.25 < 0.5` и выбирает `ok_path`.
3. `alert_path` получает статус `skipped`.
4. DAG завершается успешно, `on_success_callback` шлёт письмо SUCCESS.

**Что показывает сценарий:**
- ветвление может пойти в другую ветку в зависимости от условия;
- поведение меняется декларативно через Variable, без правки DAG-файла.

**Скриншоты:** `screenshots/step_2_ok_path/`

- Graph View с зелёным `ok_path` и розовым `alert_path`;
- детали задачи `ok_path`.

### Сценарий C — полное падение DAG

**Настройки:**
- `missing_ratio_threshold = 0.1` (чтобы пойти в `alert_path`);
- `alert_fail_always = true`.

**Что происходит:**

1. `branch_by_threshold` выбирает `alert_path`.
2. `alert_path` падает на всех 4 попытках (1 + 3 retry).
3. Задача становится `failed` (красная).
4. `finalize` не запускается.
5. DAG завершается с ошибкой, `on_failure_callback` шлёт письмо FAILED.

**Что показывает сценарий:**
- retry-политику при постоянном сбое;
- `on_failure_callback` на уровне DAG;
- корректную остановку пайплайна при неуспехе.

**Скриншоты:** `screenshots/step_3_failed/`

- красный `alert_path` с `failed`;
- DAG в статусе failed;
- логи с 4 попытками;
- письмо FAILED в MailHog.
