# ADR. Использование Spring Batch для пакетной обработки отчётов в TradeWare

## Y-statement

| Элемент | Описание |
|---|---|
| **Контекст** | Монолит на Java 11 (WildFly) обрабатывает загрузки отчётов по остаткам в онлайн-режиме, построчно. В сутки проходит ~400 000 строк, в пиковые дни нагрузка возрастает ×2–3 (до 1,2 млн). Бизнес требует выдерживать 100–150 параллельных загрузок и обрабатывать отчёт на 2 000 строк за ≤ 30 секунд. Поток отчётов от региональных складов постоянный: файлы поступают в течение дня и должны обрабатываться в ближайшие минуты. В IT-инфраструктуре есть только файловые логи и мониторинг VM/WildFly — централизованных логов и метрик нет. Kubernetes в компании отсутствует, внедрять его не планируется. Стек: Java 11, WildFly, PostgreSQL, GCS, GCP. Попытка перейти к микросервисам (перенос БД в GCP, файлов — в GCS) не решила проблему производительности, потому что принцип обработки остался online построчным. |
| **Причина** | Проблема не в интерфейсах и не в бизнес-логике, а в отсутствии слоя пакетной обработки. Online-транзакции (приём заявок, отображение остатков) конкурируют за ресурсы PostgreSQL с batch-операциями, что в пиковые часы приводит к взаимным блокировкам и деградации. Отчётность формируется в реальном времени, хотя её можно унести в batch-обработку. Монолит не масштабируется горизонтально под 100–150 параллельных загрузок. Диагностика ошибок затруднена из-за отсутствия централизованных логов и метрик. При этом поток данных постоянный, а не «раз в сутки» — значит, нужен воркер, всегда готовый принять новую порцию, а не редкий job по внешнему расписанию. |
| **Принято** | Внедрить **Spring Batch** как batch-фреймворк для пакетной обработки отчётов по остаткам. Spring Batch обеспечивает chunk-oriented processing, транзакционность на уровне чанка, встроенные retry/skip/restart, поддержку partitioning и multi-threaded step. **Spring Scheduler** внутри Spring Boot приложения (`@Scheduled` с конфигурируемым интервалом) запускает Spring Batch Job и опрашивает GCS на предмет новых файлов (polling). Развёртывание — **Docker-контейнер на Compute Engine VM** в GCP, рядом с монолитом, в привычной среде без новых инфраструктурных слоёв. Наблюдаемость — **Micrometer → Prometheus → Grafana** (метрики) + **Loki/ELK** (логи). Интеграция с текущим стеком: Java 11, Spring, PostgreSQL, GCS. |
| **Отклонено** | **K8s CronJob** — избыточен: Kubernetes в компании нет, внедрять его ради одной задачи нецелесообразно; поток данных постоянный, а не «раз в сутки», поэтому внешний cron не соответствует природе нагрузки. **Cloud Scheduler / Cloud Run Job** — GCP-native, но это новый инфраструктурный слой ради одной задачи; Spring Scheduler уже даёт всё, что нужно. **Apache Airflow** — Python-стек, чужой для Java-команды, требует отдельного постоянного компонента (webserver, scheduler, metadata DB), избыточен для одной задачи. **Spring Cloud Data Flow** — нативнее для Spring-экосистемы, но это дополнительный инфраструктурный слой, не заменяющий Spring Batch, а оркестрирующий его; при одном воркере не даёт выигрыша. **Temporal** — workflow engine для долгоживущих процессов с состоянием (saga, компенсации, длительные таймеры); не предназначен для chunk-oriented batch-обработки; дал бы гибкую оркестрацию, но потребовал бы вводить новый стек и не решал бы задачу обработки 400k строк/сутки напрямую. **Camunda** — BPMN-движок для бизнес-процессов; аналогично Temporal, не для batch-обработки данных. **Apache Spark** — распределённый движок для big-data; для 400k строк/сутки это оверкилл: сложная инфраструктура (driver, executors, cluster manager) без реальной отдачи на таких объёмах. |
| **Цель** | Разгрузить online-контур: тяжёлые операции уходят в отдельное Spring Batch-приложение, работающее чанками, что снижает нагрузку на PostgreSQL. Обеспечить горизонтальное масштабирование до 150 параллельных загрузок через partitioning и multi-threaded step. Уложиться в SLA: 2 000 строк ≤ 30 секунд. Закрыть пробел в наблюдаемости: централизованные логи, метрики, алерты. Подготовить путь к микросервисам: batch-компоненты выносятся из монолита как самостоятельные сервисы, не нарушая работу online-части. Совместимость с текущим стеком (Java, Spring, Postgres, GCS, GCP) и минимальный порог входа для команды. Минимизировать количество новых инфраструктурных компонентов. |
| **Компромиссы** | Привязка к Java/Spring-стеку — сложнее привлекать специалистов других профилей. Воркер висит в памяти 24/7 (небольшой расход CPU/RAM), но это оправдано постоянным потоком файлов — он должен быть готов принять новую порцию в любой момент. Расписание и логика Job’а связаны с релизным циклом: изменение интервала polling’а или cron-выражения Spring Scheduler требует пересборки и передеплоя приложения — но для одного воркера это приемлемо. Нужно выстроить CI/CD для batch-приложения отдельно от монолита. Разработчикам потребуется дисциплина в проектировании Job-ов: идемпотентность, обработка дублирующихся файлов, корректная работа с partial failures. Если в будущем появится несколько batch-воркеров с разными расписаниями, имеет смысл рассмотреть централизованный оркестратор (Spring Cloud Data Flow или Airflow) — но это отдельный этап эволюции. |

## Дополнительные пояснения

### Почему Spring Scheduler, а не внешний cron

Поток отчётов от региональных складов **постоянный**: файлы приходят
в течение дня, а не «раз в сутки в полночь». Воркер должен быть готов
обработать новую порцию в ближайшие минуты после её появления.

Внешний cron (K8s CronJob, Cloud Scheduler, Cloud Run Job) хорош, когда:
- запусков мало и они редкие (например, раз в сутки);
- приложение не хочется держать в памяти постоянно;
- нужно централизованное управление десятками расписаний.

В нашем случае:
- запусков много, они частые, поток непрерывный;
- приложение всё равно должно быть в памяти, чтобы быстро реагировать;
- расписание одно, централизованное управление не нужно.

Поэтому **Spring Scheduler внутри воркера** — самый простой и адекватный
выбор. Он не требует ни новых инфраструктурных компонентов, ни
дополнительных навыков у команды.

### Как работает polling

1. `@Scheduled(fixedDelay = 30_000)` — метод `pollAndProcess()` вызывается
   каждые 30 секунд после завершения предыдущего вызова.
2. Метод обращается к GCS, получает список новых файлов отчётов
   (по префиксу, по метаданным, по дате).
3. Для каждого нового файла запускается Spring Batch Job.
4. Job читает файл чанками, валидирует, обогащает справочными данными,
   пишет в БД номенклатуры.
5. Результаты (успех/ошибка) фиксируются в метриках и логах.

Интервал polling’а конфигурируемый (`@Scheduled` поддерживает property-placeholder).
Параллелизм Job’ов регулируется через `TaskExecutor` Spring Batch.

### Что даёт Spring Batch

- **Chunk-oriented processing** — вместо построчных UPDATE обрабатываем
  пачками (например, 1000 строк). Снижает нагрузку на Postgres в разы.
- **Транзакционность на чанк** — сбой откатывает только текущий чанк.
- **Retry / Skip / Restart** — встроенные механизмы.
- **Partitioning** — разделение диапазона данных между воркерами.
- **Multi-threaded step** — параллелизм внутри одного Job.

### Что дали бы Temporal / Camunda (почему не выбрали)

- **Temporal** — workflow engine для сложных бизнес-процессов с состоянием,
  компенсациями, длительными таймерами. Для batch-обработки данных не даёт
  преимуществ: логика простая (читай-обрабатывай-пиши), а инфраструктурные
  затраты высоки.
- **Camunda** — BPMN-движок для бизнес-процессов с ручными шагами,
  согласованиями, ветвлениями. В задаче этого нет — только детерминированная
  обработка данных.

Оба инструмента могли бы применяться **в дополнение** к Spring Batch
для оркестрации сложных сценариев в будущем, но не как замена.

### Что дал бы Spark (почему не выбрали)

Spark — распределённый движок для big-data с объёмами от десятков гигабайт.
400 000 строк в сутки — это несколько мегабайт. Использование Spark на таких
объёмах — избыточная инфраструктура без реального выигрыша. Плюс это
Scala/Python-экосистема, что усложнило бы интеграцию с Java-стеком.
