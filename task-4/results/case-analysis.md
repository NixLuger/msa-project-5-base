# Анализ проблем кейса TradeWare

## 1. Контекст компании

TradeWare — SaaS-платформа для малого и среднего бизнеса: API для складского
учёта стройматериалов, управления остатками и логистикой между складами.

**Текущая архитектура:**
- Монолит на Java 11, WildFly.
- PostgreSQL (БД номенклатуры + БД справочных данных).
- Google Cloud Storage — файлы отчётов.
- Angular + WebSockets — фронтенд.
- GCP / Compute Engine — хостинг (VM, Docker, Docker Compose).

**Пользователи:** сотрудники склада, менеджеры, партнёры, аналитики.
**Сезонность:** пики — весна и лето, строительный сезон.

## 2. Проявление проблем

| Категория | Симптом |
|---|---|
| Производительность | Отчёты по остаткам «висят», обновления позиций приходят с задержкой или не применяются |
| Производительность | ERP-интерфейс замедляется при формировании складских заданий и приёме материалов |
| Масштабируемость | В пиковые дни нагрузка ×2–3, система перегружается, падает операционная эффективность |
| Масштабируемость | 100–150 параллельных загрузок в пиковые часы система не выдерживает |
| Наблюдаемость | Нет централизованных логов — только файлы |
| Наблюдаемость | Нет метрик приложений — только стандартный мониторинг VM и WildFly |
| Наблюдаемость | Ошибки трудно диагностировать: логи и метрики не сводятся в одну картину |
| Архитектура | Монолит обрабатывает каждую запись онлайн, построчно |
| Архитектура | Отчётность формируется в реальном времени, хотя её можно унести в batch-обработку |
| Архитектура | API для партнёров и региональных складов страдают от взаимных блокировок |

**Бизнес-последствия:**
- задержки в планировании снабжения;
- просрочки поставок;
- неэффективная логистика;
- цепные задержки у клиентов;
- финансовые и репутационные риски.

## 3. Root cause

Проблема **не в интерфейсах и не в бизнес-логике**. Монолит работает стабильно
при низкой нагрузке. Проблема — в **отсутствии слоя пакетной обработки данных**
и, как следствие, в **смешении online- и batch-нагрузки в одном монолите**.

Онлайн-транзакции (приём заявок, отображение остатков) конкурируют за ресурсы
Postgres с batch-операциями (загрузка отчётов, обновление справочников,
построчные UPDATE). В пиковые часы конкуренция становится критической.

Попытка миграции в микросервисы (перенос БД в GCP, файлов — в GCS) не решила
проблему, потому что **сам принцип обработки остался online построчным**.
Микросервисы без batch-слоя воспроизводят ту же архитектурную ошибку.

**Важный нюанс:** поток отчётов от региональных складов **постоянный**,
а не «раз в сутки в полночь». Остатки приходят в течение дня и должны
обрабатываться в ближайшие минуты. Это принципиально влияет на выбор
планировщика: нужен воркер, постоянно готовый принять порцию данных,
а не редкий ночной job.

## 4. Требования к решению

### Функциональные

- Обработка ~400 000 строк в сутки (пик — до 1,2 млн при ×3).
- 100–150 параллельных загрузок отчётов в пиковые часы.
- Обработка отчёта на 2 000 строк — **≤ 30 секунд**.
- Валидация формата и целостности данных.
- Обновление позиций справочной информацией (промо, характеристики).
- Загрузка результата в БД номенклатуры.
- Уведомление пользователя об успехе или ошибке.
- Реакция на новые файлы в GCS в течение минут (не «на следующий день»).

### Нефункциональные

- **Наблюдаемость:** централизованные логи, метрики, алерты.
- **Масштабируемость:** возможность увеличить параллелизм обработки.
- **Отказоустойчивость:** retry, обработка сбоев, отсутствие потери данных.
- **Совместимость:** интеграция с текущим стеком (Java 11, Spring, Postgres, GCS, GCP).
- **Путь к микросервисам:** постепенный вынос функционала из монолита.

### Ограничения

- Стек: Java 11, WildFly, PostgreSQL, GCS, GCP.
- Команда — Java/Spring-разработчики, есть DevOps.
- Инжиниринг-лид имеет опыт работы со Spring Batch.
- **Kubernetes в компании нет и внедрять его не планируется** на этом этапе.
- **Новые инфраструктурные компоненты допустимы только при явной
  необходимости.** Принцип «минимум изменений»: если задачу можно решить
  средствами текущего стека — решаем ими.
- Миграция должна быть постепенной, без «большого взрыва».
- Поток данных постоянный, поэтому batch-воркер должен быть всегда готов
  принять новые файлы, а не просыпаться раз в сутки по внешнему cron.

## 5. Вывод

Ключевая потребность — **вынести тяжёлые операции из online-контура
в пакетный слой**. Это разгрузит транзакционные ресурсы Postgres,
позволит масштабироваться и подготовит систему к росту бизнеса.

Параллельно нужно закрыть пробел в наблюдаемости. Дополнительные технологии
должны вводиться осознанно и только те, которые действительно решают задачу:
внешний cron-планировщик или Kubernetes здесь избыточны — поток постоянный,
а один воркер не требует централизованного расписания.
